# NOERIVA · 澄观 — V5 高性能架构修订说明

**修订日期：2026-09-06**  
**状态：架构规范已修订；未实现、未部署、未进行负载测试。**  
依据：原 `NOERIVA_MASTER_PROMPT.md` V4、设备中心设计评审 R1、用户“请按照你认为性能最强的方法 改善现在的架构”的委托，以及本包 `docs/SOURCES.md` 中的官方技术资料。

## 1. 这次直接确定的架构

采用 **MySQL 控制面 + VictoriaMetrics 指标热存储 + Kafka 事件总线 + ClickHouse 结构化历史与汇总 + 选择性 Elasticsearch 文本检索 + Redis 当前状态/查询缓存 + S3 兼容证据存储**。

不是把所有数据依次经过这些组件，也不是每条记录保存七份。每一类数据只有明确的主存储，其他副本必须说明用途、成本、保留期及重建方式。选择针对 NOERIVA 的值守、设备诊断、带宽热力图和历史归因负载，不声称它对任意硬件、任意查询都是世界最快。

本次用户委托允许修改目标架构并选定技术方向；不视为生产切换、购买商业许可、删除历史数据或真实设备写入的授权。

| 原 V4 | V5 目标基线 | 目的 |
|---|---|---|
| Prometheus 是主要数值时序存储，长期方案后期再评审 | VictoriaMetrics 承担指标热存储，保留 Prometheus 采集兼容；长期产品汇总进入 ClickHouse | 从开始就定义历史分辨率、保留和查询成本 |
| Redis Streams 初期承担事件总线 | Kafka 承担离散事件、日志、Flow/NAT 的可靠传输与重放；Redis 回归可重建缓存 | 将持久积压与缓存驱逐分开，支持独立消费者 |
| 大量日志、审计和 Flow 面向 Elasticsearch | ClickHouse 承担结构化历史与统计，ES 按必要字段和时间范围派生索引 | 不为每个高容量明细都支付完整文本索引成本 |
| 设备页面围绕多个领域接口组合，当前态读模型未充分规定 | 设备当前状态投影、批量查询、历史和汇总分路 | 设备页不随历史总量增长而反复扫描历史 |
| 原始指标直接支撑较多历史图表 | 近期细粒度查询 + 可修正的 5 分钟/小时汇总 | 热力图和长期趋势读取与画面粒度相匹配的数据 |
| MinIO 是固定对象存储依赖 | ObjectStore 采用 S3 接口；现有 MinIO 兼容迁移，新部署核验维护中的供应商 | 解除已归档上游的强制依赖 [S15] |
| 多项性能与长期存储决定延至 Phase 13 | Phase 0 确定契约，Phase 1–4 验证关键查询链路，Phase 13 扩展和故障验证 | 不让数据设计成为末期补丁 |

原有服务器、BMC、路由交换、配置审计、NAT、VPN、AAA、DHCP、DNS、未知 Trap、合成探测、证据与灾备等能力范围保留。Vue 3 / TypeScript / Vite、Query / Pinia 分工、B / Clarity 浅色与 44px 行高保留。

## 2. 两条采集链路，不让普通数值样本绕远路

### 指标链路

```text
设备 / exporter / NoerivaEdge 指标适配器
    → 站点 vmagent（批量、压缩、有界磁盘缓冲）
    → VictoriaMetrics（细粒度近期指标）
    → 受限的 Java 聚合任务
    → ClickHouse（5 分钟 / 小时产品汇总）
```

温度、CPU、内存、接口计数器等，不逐样本包装完整审计 JSON，不默认经过 Kafka，不重复写进 MySQL 和 Elasticsearch。采集适配器仍由 Java / NoerivaEdge 管理；vmagent 是基础设施采集组件，不意味着新增应用语言。[S01][S19]

设备健康变化、采集缺口、源重启、合并后的设备摘要属于低频领域事件，可以进入事件链路。指标写入与“写入完成通知”不是一个事务：聚合任务必须有周期性核对，不能丢一条提示就永远不生成历史桶。

### 日志、事件与审计链路

```text
设备事件 / Syslog / Flow / NAT / 身份会话
    → Edge 本地持久缓冲
    → mTLS 批量接入
    → Kafka
        ├→ Java / Kafka Streams：标准化、受限去重、生命周期投影
        ├→ ClickHouse：结构化历史与查询视图
        ├→ Elasticsearch：确有必要的脱敏文本索引
        ├→ ObjectStore：获准保留的原始批次与证据
        └→ 当前状态、告警、SSE 版本通知
```

Kafka 是这次性能架构的明确选择，不再只是未来备选；理由是多消费者、积压隔离、可靠重放等目标要求，不是已经测得 Redis 无法承载百万条/天。已有 Redis Streams 实例通过有界迁移退出，而不是直接删除。

`RECEIVED / DURABLY_QUEUED / QUERYABLE / EVIDENCE_ARCHIVED` 分开记录。API 收到数据，不等于历史已可查询；Kafka 确认，不等于证据已归档。跨库不假设全局事务，禁止为了漂亮状态把未完成阶段标成完成。

## 3. 设备页的主要加速点：维护“现在”，而不是每次从历史推导

建立 `device_current`、`interface_current` 读模型，保存健康、可达性、关键指标摘要、活动告警数、来源时间、版本及采集状态。配置和告警处置仍以 MySQL 为准；Redis 保存可重建的快速表示。

重大状态变化及时更新，普通摘要合并后更新，初始可测试 5 秒合并周期；不把每个标量样本变成一条 MySQL UPDATE。补传旧数据不能把新状态覆盖回旧状态，重新接收到旧样本也不能刷新其“新鲜度”。主机与 BMC 的来源时间独立。

| 前端区域 | 读路径 |
|---|---|
| 设备列表、当前健康 | MySQL 资产/状态检查点 + 批量 Redis 状态 |
| 最近一小时曲线 | VictoriaMetrics 有界范围查询 |
| 七天带宽热力图 | ClickHouse 已完成小时汇总 + 当前未完成小时 |
| 三个月容量趋势 | ClickHouse 合适分辨率汇总 |
| 设备活动 | ClickHouse 按设备/时间查询，文本需求路由 ES |
| 设备连接图 | 当前拓扑范围查询 + 小批量遥测补丁 |
| NAT/IP 历史归因 | 候选索引 + 最新区间版本 + 历史身份依据 |

设备列表禁止逐行发一次指标查询。一个设备页面也不必等待所有数据库都成功：各区块独立返回时间、新鲜度、覆盖率和局部失败。

对配置变更、告警确认等事务操作，用 MySQL 同事务 outbox 发出变更；操作响应直接返回已提交版本。不能因随机读取落后副本而让刚确认的告警“又变回未确认”。[S14]

## 4. 七天带宽热力图：168 个展示格，而不是每次读取所有原始点

以每 15 秒采样、单接口单方向为例：七天共有 40,320 个原始样本，正常日历布局只有 168 个小时格。读取已维护的小时桶，相比重复读取原始点，逻辑点数减少约 240 倍；这不是承诺端到端速度提高 240 倍。

小时桶保留有效时长、有效字节增量、覆盖率、已观测峰值、样本数、来源、算法版本和修订版本。平均带宽定义为：

```text
平均 bps = 8 × 有效字节增量之和 / 有效观测秒数之和
```

无有效时长为未知，不是零。计数器重启/回绕、接口身份改变、跨桶插值和缺口都保留标志；峰值是已观测窗口峰值，不是保证捕捉到了瞬时线速峰值。

Prometheus 数值样本采用浮点表示，因此不能保证保存所有 UInt64 计数器的每一位。需要精确原始计数器证据时，使用独立获准的原始对象或整数安全的类型化记录，而不把浮点指标宣称为逐字节审计底稿。[S17]

已结束小时读汇总；当前小时读有界原始窗口或临时汇总并标记未结束。迟到数据将相关桶标脏，生成新的完整桶版本并使缓存失效，不能用简单累加让重试造成双倍带宽。

历史聚合按事件时间，不能直接以默认摄入时间聚合替代；尤其站点断网后补传的数据不能都算进恢复时刻。vmagent 默认流式聚合有摄入时间与内存状态边界，V5 不将它作为唯一历史来源。[S02]

七天使用工作区 IANA 时区的自然日。UTC+05:30 等时区用更细桶对齐本地小时，夏令时重复/缺失小时显式记录。超过保留分辨率不能精确重建时，返回限制而不补造精度。正方形指绘图区；7×24 单元矩阵不可能同时要求每格正方形且铺满正方形。

## 5. ClickHouse：针对查询建表，不能只换数据库名

结构化数据分领域表：Flow、NAT 生命周期、身份分配、日志事件、指标汇总等。设备活动主要按设备和时间访问；NAT 归因经常从公网 IP / 端口 / 协议开始，因此需要独立的候选访问路径，不能所有表都只按设备组织。[S10][S11]

NAT 查询采用：

```text
授权与时间范围
    → 公网/内网候选索引（包含早于当天创建但仍可能有效的记录）
    → 选择每个候选的最新发布版本
    → 验证修订后的有效时间区间
    → 关联当时的 VPN / DHCP / AAA
    → 返回依据、冲突、时钟和采集缺口
```

缺少 DELETE 不代表永久有效；公网 IP 和端口不是跨网关/VRF 的全局唯一键。候选索引落后时，不得把“尚未查到”报告成确定的 `NO_MATCH`。

高流量路由器不能把全部 Flow 写入压在一个设备分片。按稳定流标识/虚拟桶分散高容量明细，生命周期运算在必要时按关联键重新分组。分区键、排序键和分片键分别设计，投影不会自动解决跨分片路由。

批量写入、压缩及增量物化可以降低重复计算，但正确性边界不能省略：Kafka 事务不自动覆盖外部库；官方 ClickHouse sink 的 exactly-once 需要特定配置；ReplacingMergeTree 的后台合并不等于查询立即去重。修订汇总使用完整快照及版本，而不是默认可重复求和的增量。[S06][S08][S09][S10]

## 6. 查询隔离：确保调查和导出不拖垮值守台

在 API 和存储两端实施查询类别：

- `INTERACTIVE_STATE`：设备摘要、当前告警，保留小查询配额。
- `INTERACTIVE_CHART`：限制设备/序列数、范围、分辨率和扫描量。
- `INVESTIGATION`：独立内存、并发与证据权限。
- `BATCH_EXPORT` 与 `REPLAY_REBUILD`：服务器受限后台作业，不占满交互资源。

仅在 SQL 末尾加 LIMIT 不限制前面的扫描。浏览器取消必须传到数据库查询，而不只是关闭 HTTP 响应；结果缓存必须含权限/脱敏版本，并在命中时重新检查授权。[S12]

不同 API 线程池不等于磁盘隔离。分开的 vmselect 仍可能竞争同一组 vmstorage；ClickHouse 读取副本仍需要复制和合并。发生实测争用时，才扩展为独立汇总服务节点/集群，明确额外副本和滞后成本。

## 7. 保留策略与存储层次

候选指标策略：原始 30 天；5 分钟汇总 180 天；小时汇总 730 天。它们是待验证的容量策略，不是已启用的 TTL。

保留期与后台聚合进度不天然联动。不能假设聚合落后时 VictoriaMetrics 会按外部水位自动停止过期；需要提前监测余量，获准后延长保留或及时保存危险窗口。未及时保存的历史，只能报告无法重建。

会话审计不能照搬指标降采样：NAT / VPN / DHCP / AAA 的保留要能组成同一历史证据链。原始归档按批次组织，不是一条事件一个对象；派生 Parquet 不自动等于原始字节。应用有效期、物理后台清理、备份期限、保留锁分别管理。

MinIO 社区上游在 2026-04-25 归档且声明不再维护，因此 V5 不再强制新生产环境采用该组件。保留已有 MinIO 的兼容适配器与对象引用，新对象存储通过 S3 接口接入；具备运维条件时以 Ceph RGW 作为自建参考，也可使用获准的受支持 S3 服务。S3 接口兼容不等于 Object Lock 和恢复能力已经通过测试。[S15][S16]

## 8. 单机效率、高可用与横向分片分开

相同硬件下，集群会增加进程间和网络开销。VictoriaMetrics 官方也区分单机效率与集群扩展性。因此，不把“最多节点”误当作“性能最强”。[S01]

`COMPACT` 是单实例集成验证档；`HA_PERF` 是独立故障域生产参考：Kafka 三 broker、VM 分离接入/查询/存储、ClickHouse 副本、MySQL 单主组等；`SCALE` 再按测得瓶颈添加分片或独立查询资源。完整数量与代价见 Master H10。参考数量不是采购清单，不代表当前硬件足够。

对于有两个副本的 ClickHouse，如果严格要求两份确认，一份失败会使该类落库暂停，由 Kafka 承接积压；需要故障下继续落库时再评估三副本/两份确认。不能同时暗示零损失、零等待和最小成本。[S13]

热数据优先评估本地 NVMe/SSD；Kafka 日志、ClickHouse 合并、VM 文件和对象归档需独立 I/O 预算或经过测试的隔离。不要把所有重负载塞进同一慢盘阵列，再用更多容器掩盖争用。CPU 指令集、内存、网卡与所选发行包兼容性须对真实主机核验。

## 9. 可验收的目标与实际状态

下列是初始测试目标，不是测量结果：设备摘要 p95≤200ms；前100条设备列表≤300ms；单接口七天热力图≤300ms；10条趋势曲线≤750ms；有界 NAT 元组查询≤1000ms。所有目标必须绑定硬件、活动序列/事件规模、并发、冷/热缓存与持续写入条件。

验收同时加入后台合并、补传、备份、节点故障和权限撤销。只测空库 INSERT 或缓存命中不合格；副本和备份必须进行恢复演练，不能承诺未经验证的 RPO=0。

使用 **`NOERIVA_MASTER_PROMPT_V5.md`** 作为新的单一规范，不再把旧 V4 和 V5 作为同等优先级同时输入。V5 已内嵌 H01–H12 性能契约、原有领域范围和来源说明；本文件只是中文导读。
