# Existing two-node K3s data plane

This bundle supplies the data dependencies missing from the application Helm Chart. It is intended for the existing K3s v1.36.4 cluster: `argus-primary` (192.168.4.62) has `noeriva.io/data-plane=true`; `argus-worker` (192.168.4.63) may run application replicas. The unrelated NotReady edge node is not selected. Root deployment work owns node labels, the namespace, the existing Secret, image import, app Helm values, the LAN entry point and backups.

All six data services are **single instances pinned to node 62**, with local-path PVCs. This is a usable compact deployment, not data HA. Loss of node 62 interrupts MySQL, Redis, Kafka, ClickHouse, VictoriaMetrics and Elasticsearch, even if application replicas remain on node 63. Local-path storage does not move the data to another node automatically. Two physical machines do not provide three-member failure tolerance; do not add a second embedded-etcd server and call it HA. See [K3s embedded-etcd requirements](https://docs.k3s.io/datastore/ha-embedded) and [local-path storage behavior](https://docs.k3s.io/add-ons/storage).

## Resources and application endpoints

All Services use ClusterIP, with no NodePort, hostPort, hostNetwork or external address. Namespace: `noeriva-system`. The cluster DNS domain is assumed to be `cluster.local`; Kafka's advertised listener and quorum voter must be adjusted together if that differs.

| Service | Application endpoint | Storage request / limit |
|---|---|---|
| noeriva-mysql | `r2dbc:mysql://noeriva-mysql:3306/noeriva`; Flyway `jdbc:mysql://noeriva-mysql:3306/noeriva?allowPublicKeyRetrieval=true&sslMode=DISABLED` | 20Gi PVC; 1Gi RAM limit |
| noeriva-redis | host `noeriva-redis`, port `6379`, TLS false | 1Gi PVC; 256Mi RAM, Redis maxmemory192mb |
| noeriva-kafka | `noeriva-kafka:9092`, security protocol `PLAINTEXT` | 20Gi PVC; 1Gi RAM, heap256–512Mi |
| noeriva-clickhouse | `http://noeriva-clickhouse:8123`, user `noeriva` | 100Gi PVC; 2Gi RAM requested, 6Gi limit |
| noeriva-victoriametrics | `http://noeriva-victoriametrics:8428` | 50Gi PVC; 768Mi RAM |
| noeriva-elasticsearch | `http://noeriva-elasticsearch:9200`, authenticated internal endpoint | 20Gi PVC; 2Gi RAM, 512Mi heap |

Runtime settings remain application Helm values, which are outside this directory. The current VM client uses one base URL for `/api/v1/import`, `/api/v1/query_range` and raw exports; this single-node VM serves those paths. A future VM cluster needs appropriate routing, not an arbitrary vminsert or vmselect URL.

Every data Pod has `noeriva.io/data-plane: "true"`; application egress can select that label with TCP ports3306/6379/9092/8123/8428/9200. All workloads use `nodeSelector: {noeriva.io/data-plane: "true"}`. Only node62 should receive that label. Bootstrap Pods share the label but have separate component selectors, so Services do not route to Jobs.

MySQL8.4.11, Redis8.2.9-alpine, Kafka4.3.1 and VictoriaMetrics1.151.0 match [Compose](../../compose/compose.yaml). ClickHouse is pinned to **26.3.32.14 LTS** for node62's Intel Xeon E5-2650 v2. The original26.8.2.7 amd64 image exited132 with an invalid CPU instruction before initialization: its [versioned Docker requirements](https://github.com/ClickHouse/ClickHouse/blob/v26.8.2.7-lts/docker/server/README.md#compatibility) require x86-64-v3/AVX2, absent on this processor. The [26.3.32.14 build defaults](https://github.com/ClickHouse/ClickHouse/blob/v26.3.32.14-lts/cmake/cpu_features.cmake) retain x86-64-v2/SSE4.2. This compatibility choice was made while the new database was empty; it is not permission to downgrade an existing26.8 data directory. Both server and initialization client must use the compatible version.

The manifests use version tags and `IfNotPresent`. They deliberately do not copy local arm64 resolved digests. Import the corresponding **linux/amd64** images into the actual K3s containerd runtime on node62 and record resolved imageIDs after startup; Docker's image store is not automatically K3s's containerd image store. Offline image packaging is part of deployment work.

## Existing Secret contract

Create or securely transfer the existing `noeriva-runtime` Secret before applying the workloads. No Secret or credential value is generated by this bundle.

| Key | Used by |
|---|---|
| SPRING_R2DBC_PASSWORD | MySQL `noeriva` application account initialization |
| NOERIVA_DB_ROOT_PASSWORD | MySQL root initialization; distinct from the application password |
| SPRING_DATA_REDIS_PASSWORD | Redis authentication and probes |
| NOERIVA_CLICKHOUSE_PASSWORD | ClickHouse user initialization and schema Job |
| NOERIVA_ELASTICSEARCH_PASSWORD | Elasticsearch bootstrap and application search client |

The application Secret additionally needs its existing bootstrap, collector, metrics, Flyway and device-credential encryption keys. In particular, preserving `device_connection` rows requires the original `NOERIVA_CREDENTIAL_KEY`; copying the database with a newly generated encryption key cannot restore the saved device credentials. Do not print the Secret, decrypted connection records or expanded environment configuration.

MySQL environment initialization applies only to an empty data directory. Changing a Secret does not rotate existing MySQL user passwords. Restoring an existing database also preserves its `app_user` password hashes: the application bootstrap uses `INSERT IGNORE`, so a new bootstrap password does not overwrite an existing admin account.

## Application order

These commands describe the deployment order for the authorized operator. See the acceptance record below for the checks actually completed on the target cluster.

1. Prepare the namespace/labels, Secret, imported amd64 images and persistent storage. Confirm node62 is the only data-plane node and the `local-path` StorageClass binds storage to the selected node.
2. Apply the deny-by-default data policies before starting the workloads:

```sh
kubectl apply -f deploy/kubernetes/two-node/network-policies.yaml
kubectl apply -k deploy/kubernetes/two-node
kubectl -n noeriva-system rollout status statefulset/noeriva-mysql --timeout=300s
kubectl -n noeriva-system rollout status statefulset/noeriva-redis --timeout=180s
kubectl -n noeriva-system rollout status statefulset/noeriva-kafka --timeout=300s
kubectl -n noeriva-system rollout status statefulset/noeriva-clickhouse --timeout=300s
kubectl -n noeriva-system rollout status statefulset/noeriva-victoriametrics --timeout=180s
kubectl -n noeriva-system wait --for=condition=complete job/noeriva-kafka-init-v1 job/noeriva-clickhouse-init-v1 --timeout=500s
```

3. Verify/restore the intended data and only then deploy the application. MySQL Flyway V1–V7 is run by the application; this bundle does not contain a separate MySQL migration Job. Keep the previous worker stopped during cutover and enable only one assigned NOERIVA worker after all endpoints are consistent.
4. Check application authentication, actual data queries, ClickHouse events/rollups, VM sample publication, worker heartbeat and authorized device collection. A TCP or `/ping` probe alone does not prove these workflows.

Kafka initialization creates and verifies the three versioned topics with3 partitions and RF1: `noeriva.events.v1`, `noeriva.events.dlq.v1`, `noeriva.control.v1`. It configures minISR1 and no retention-age/byte deletion when creating topics. Existing topics are not silently repartitioned or reconfigured; a conflicting partition count/RF fails the Job. For restored topics, inspect the retention/minISR configs as well.

ClickHouse initialization executes the two checked-in SQL files and verifies that both expected tables exist with `ReplacingMergeTree`. `CREATE TABLE IF NOT EXISTS` does not repair an incompatible existing schema; check schema compatibility before restoring historical data. ConfigMap names have content hashes, and stateful configuration changes cause a Pod rollout. Job templates are immutable: to rerun updated initialization, delete only the two named initialization Jobs and reapply the bundle. Do not delete StatefulSets or PVCs to rerun schema initialization.

Both Jobs have activeDeadlineSeconds480 and backoffLimit2. The retained Job status/logs are available for review. If a Job has retried, inspect its succeeded Pod's logs explicitly; `kubectl logs job/...` can choose an earlier failed Pod. Kafka's Service publishes not-ready addresses so its single KRaft controller can resolve itself during startup; the bootstrap Job still verifies broker readiness and topics before the application is enabled.

## Isolation, storage and operating limits

- The seven NetworkPolicies allow data ingress only from same-namespace NOERIVA control/worker Pod labels and the matching bootstrap Job. Kafka can reach its own broker/controller ports. Bootstrap egress is only DNS plus its own data service. No ingress peer grants access to the old `argus` namespace. Ordinary Pods there should fail data-port connectivity; verify this in the real cluster. Kubernetes policies are additive, so another broad allow-policy selecting these Pods must not undermine the restriction.
- DNS egress assumes CoreDNS in kube-system with `k8s-app=kube-dns`. Internal data traffic is plaintext and authenticated where supported. NetworkPolicy is not TLS, and it does not isolate host-root access or a trusted operator who can create same-namespace Pods. Kafka and VM rely on network isolation for their unauthenticated internal endpoints.
- Native ClickHouse9000 is allowed only for its schema Job; Kafka9093 only for its own Pod. ClickHouse9363 is declared for future metrics collection but has no observability ingress allowance in this bundle. The existing Compose vmagent scrape targets do not automatically work in Kubernetes; protected Pod discovery and an explicit metrics policy are separate work.
- All containers are non-root, drop ALL capabilities, disallow privilege escalation, use RuntimeDefault seccomp and a read-only root filesystem. PVC ownership and writable tmp/runtime/config mounts are explicit. MySQL UID999/GID999; Redis UID999/GID1000; Kafka UID/GID1000; ClickHouse UID/GID101; VM UID/GID65534. Actual amd64 startup under these settings was verified on node62; future images and new clusters still require their own admission and startup checks.
- PVC retention is Retain for StatefulSet deletion and scale-down. That does not protect a PVC explicitly deleted by an operator or namespace deletion. The default local-path PV reclaim policy can still delete the underlying directory when its PVC is deleted. Back up before deleting namespaces or claims.
- Redis preserves Compose's cache semantics: RDB and AOF are disabled. Its mounted PVC does **not** make sessions persistent; restarts can require login again. MySQL/Kafka/ClickHouse/VM hold the authoritative state and history that need separate backups.
- PVC requested sizes total211Gi; local-path requests are not proof of filesystem quotas or free-space reservations. Kafka has no automatic retention deletion, ClickHouse SQL has no TTL and VM uses100-year retention. Monitor disk growth and preserve a recovery copy outside node62. Replicas are not backups.
- Application HPA and its database pool limits must be coordinated with this single MySQL. Each current application process permits24 R2DBC connections; six API Pods plus a worker can theoretically request168 before migration connections. Start with the intended two API Pods and a single worker, then scale from measured database/resource capacity.

## September 9 remediation additions

`elasticsearch.yaml` adds authenticated Elasticsearch 9.5.3 as an internal ClusterIP service. Its official amd64 manifest is `sha256:7b69d47de433699d6df59ef2d14d82d1b0f5a14ed48cf0244a6b20cc4222484e`. Native ML is disabled because the physical data node lacks AVX2; entity search does not use ML. HTTP transport stays inside the existing network-policy boundary. It runs as UID/GID1000 with dropped capabilities; the official entrypoint needs writable configuration/keystore files, so this additional container does not use the original five services' read-only root-filesystem setting. The added 20Gi claim raises requested PVC storage to211Gi.

Preserve the runtime Secret and add one independently generated `NOERIVA_ELASTICSEARCH_PASSWORD`; changing this environment variable later does not rotate an already initialized security index. Set Helm `runtime.elasticsearchUrl` and `elasticsearchUsername`, allow port9200 only to the data-plane labels, import the image on node62, then apply the service/statefulset/policy. The application incrementally processes bounded pages into a rebuildable device/interface index, verifies provider acknowledgements and current entity ownership, and reports a provider error instead of pretending search succeeded.

Flyway V10/V11 add organization settings, configuration-read leases/checkpoints, and native network-check leases. The worker reads existing registered device credentials; no new device write privileges are required. Configuration snapshots redact credentials before storage. Changing the account password revokes earlier bearer generations; deploying the new token format requires existing browser sessions to sign in again.

ClickHouse initialization v4 adds the ordered NAT receipt index. On existing installations, create the materialized view before backfilling retained events and before enabling the new all-history API. Run `scripts/backfill-nat-receipts.py` with a fixed UTC cutoff and a persisted checkpoint; select small time slices that fit the read/memory budget. The September9 installation used three-hour slices for over3.1million retained source records. A failed, partially written slice may be replayed safely: the canonical event table remains the deduplication authority. Never delete the original NAT table to rebuild this index.

The September9 acceptance run exposed two capacity defects in the initial compact profile. ClickHouse's default file-log rotation was larger than the64Mi `clickhouse-logs` EmptyDir, causing Pod eviction; the checked-in logger now uses warning level,4MiB rotation and2 archives per log (roughly24MiB across normal/error logs), plus console output. See [ClickHouse logger configuration](https://github.com/ClickHouse/ClickHouse/blob/v26.3.32.14-lts/programs/server/config.xml). The2Gi container limit also caused a global memory rejection during an8-concurrent-request smoke test, even though the affected NAT query used under7MiB. The production profile now requests2Gi and allows6Gi; the0.7 server memory ratio,12-query ceiling and per-query read/memory/time budgets remain. This production allowance differs from the smaller local Compose development profile. Apply only the updated ClickHouse ConfigMap/StatefulSet when correcting an existing deployment, preserving the data PVC and all other data services.
